# CHG-0007 — Gate 4 Team Lead Verification Governance

**Status:** APPROVED BY TEAM LEAD / EFFECTIVE ON MERGE  
**Date:** 2026-10-02  
**Issue:** #89  
**Affected governance:** Gate 4 execution workflow, Definition of Done, Gate 4 milestone promotion  
**Affected baselines:** no architecture, data, application, or runtime baseline change

## Purpose

Define Gate 4 merge governance explicitly instead of silently extending the Gate 3-only CHG-0005 record.

This is a governance/control-plane change only. It does not alter application behavior, architecture, data models, migrations, dependencies, settings, production topology, security invariants, or frozen baselines.

## Context

Gate 3 adopted Team Lead Verification through CHG-0005. That record was intentionally scoped to Gate 3 and therefore does not automatically govern Gate 4.

The initial Gate 4 kickoff draft temporarily restored mandatory independent peer approval. The Team Lead has explicitly rejected that process for Gate 4 as well: reviewers may provide useful additional evidence, but their approval must not become a mandatory merge prerequisite or be auto-requested merely to satisfy governance.

Gate 4 still retains all technical verification requirements: green CI, architecture/frozen-baseline compatibility, migration intent, security/runtime review, material-finding disposition, documentation synchronization and explicit Team Lead merge authorization.

## Decision

After the transition PR carrying CHG-0007 is merged to `dev`, the normal Gate 4 workflow is:

```text
Issue
→ short-lived branch from current dev
→ implementation + tests
→ Pull Request to dev
→ required CI green
→ Team Lead Verification
→ explicit Team Lead merge decision
```

The final Gate 4 milestone promotion is:

```text
dev
→ Pull Request to main
→ all required Gate 4 CI green, including production-smoke once introduced
→ Team Lead Verification
→ explicit Team Lead merge decision
```

Independent peer `APPROVED` review is optional. No reviewer is auto-requested solely to satisfy governance.

## Team Lead Verification gate

Before a Gate 4 PR is merged, the Team Lead verifies the applicable evidence:

1. scope is linked to an Issue or explicitly documented implementation slice;
2. the branch is synchronized with the current integration state when necessary;
3. all currently required CI jobs are green;
4. frozen Gate 3 baselines are not silently rewritten;
5. structural runtime/foundation changes have the required Change Record before implementation is merged;
6. model/migration changes, if any, are intentional and explicitly reviewed;
7. material automated/manual review findings are resolved or explicitly accepted with evidence;
8. security/privacy/runtime risks relevant to the change are covered by tests or documented verification;
9. documentation/contracts are synchronized when behavior or operating procedures change;
10. the Team Lead explicitly authorizes merge.

For Gate 4 closure/promotion, `production-smoke` becomes mandatory after #83 introduces the stable job.

## Project-brief framing

The original project brief requires production mode, production-oriented web serving, production settings/static collection and Docker/environment configuration.

Reverse proxy usage such as Nginx is listed as bonus/extra-credit scope in the brief. Gate 4 deliberately selects Nginx as the production reverse-proxy/static-serving topology because it provides a coherent public boundary and supports later optional WebSocket ingress. Documentation must not claim that the brief itself mandates Nginx.

Issue #41 real-time reporting remains optional/non-blocking.

## Transition PR itself

The PR carrying CHG-0007 is the one-time transition from the provisional Gate 4 peer-review rule to this rule.

It is explicitly authorized by the Team Lead to reach merge readiness with:

- governance/documentation-only scope;
- green repository CI;
- material findings resolved or explicitly accepted;
- Team Lead review and explicit merge decision;
- no mandatory independent peer approval.

CHG-0007 becomes effective only after that PR is merged to `dev` by the Team Lead.

## Rollback

A future change that restores mandatory peer approval must use a new governance Change Record that explicitly supersedes CHG-0007. Historical audit entries must never be rewritten to imply reviews that did not occur.

# CHG-0004 — Gate 3 Production Email Configuration Authorization

**Status:** APPROVED ON REVIEWED MERGE / NOT YET APPLIED  
**Date:** 2026-09-24  
**Issue:** #47  
**Affected baseline:** BL-FOUNDATION-001  
**Architecture dependency:** BL-ARCH-002  
**Data dependency:** BL-DATA-002  
**Feature consumers:** #26, #40

## Purpose

Authorize the smallest settings/environment-contract extension required for Gate 3 features to send
real email in production through Django's built-in email abstraction.

This Change Record is an authorization boundary. It does **not** apply production SMTP settings by
itself.

The approval becomes effective only when the Pull Request carrying this record is peer reviewed,
green in CI, and merged to `dev`.

## Why a Change Record is required

BL-FOUNDATION-001 freezes the settings/environment contract and currently documents no production
mail transport variables.

At that baseline:

- development uses Django's console email backend;
- tests use Django's local-memory email backend;
- production does not explicitly configure an email backend or SMTP connection;
- Django therefore falls back to the SMTP backend defaults when production code sends mail.

Issue #26 now requires email OTP account activation. A production deployment without a local SMTP
daemon cannot satisfy that feature using the frozen configuration.

Issue #40 will later require scheduled report email delivery and should reuse the same project-wide
Django email transport rather than inventing a second configuration path.

CHG-0003 explicitly did not authorize new production secrets or a production deployment design.
Therefore the production email contract needs its own reviewed change decision.

## Decision

CHG-0004 authorizes a bounded production email settings contract using Django's built-in SMTP
backend and no new Python dependency.

### Production email backend

`config.settings.production` may explicitly configure:

```text
EMAIL_BACKEND = django.core.mail.backends.smtp.EmailBackend
```

No third-party email SDK is authorized by this Change Record.

### Authorized environment variables

The settings/configuration layer may consume exactly these new production email variables:

```text
DJANGO_EMAIL_HOST
DJANGO_EMAIL_PORT
DJANGO_EMAIL_HOST_USER
DJANGO_EMAIL_HOST_PASSWORD
DJANGO_EMAIL_USE_TLS
DJANGO_DEFAULT_FROM_EMAIL
```

Contract:

- `DJANGO_EMAIL_HOST` — required, non-empty SMTP hostname;
- `DJANGO_EMAIL_PORT` — required positive integer;
- `DJANGO_EMAIL_HOST_USER` — required, non-empty SMTP username for the initial Gate 3 contract;
- `DJANGO_EMAIL_HOST_PASSWORD` — required, non-empty secret;
- `DJANGO_EMAIL_USE_TLS` — optional boolean with a default of `true`;
- `DJANGO_DEFAULT_FROM_EMAIL` — required, non-empty sender identity.

The implementation may add a small typed integer helper to `config.env` so host-environment parsing
remains centralized in the configuration layer.

### Settings boundary

After application, production settings may map the contract as follows:

```text
EMAIL_HOST              ← DJANGO_EMAIL_HOST
EMAIL_PORT              ← DJANGO_EMAIL_PORT
EMAIL_HOST_USER         ← DJANGO_EMAIL_HOST_USER
EMAIL_HOST_PASSWORD     ← DJANGO_EMAIL_HOST_PASSWORD
EMAIL_USE_TLS           ← DJANGO_EMAIL_USE_TLS
DEFAULT_FROM_EMAIL      ← DJANGO_DEFAULT_FROM_EMAIL
```

Services, Selectors, views, API handlers, tasks, and models must continue to use Django's email
abstraction and must not read these environment variables directly.

## Feature consumers

### Issue #26 — Authentication + email OTP activation

After CHG-0004 is approved, #26 may:

- extend `config.settings.production` with the authorized SMTP mapping;
- document the new variables in the active environment contract and `.env.example`;
- add settings-contract tests proving fail-fast/typed behavior;
- keep development console email and test locmem email unchanged.

The OTP Service must continue to call Django's email abstraction rather than SMTP libraries directly.

### Issue #40 — Scheduled report delivery

Issue #40 may later reuse the same Django email transport for report email delivery.

CHG-0004 does not authorize #40's Celery task behavior, schedules, retry policy, API delivery
credentials, or runtime services. Those remain governed by #40 and CHG-0003.

## Security requirements

The implementing feature must preserve all of these rules:

- no real SMTP credential is committed;
- `.env.example` contains placeholders only;
- the SMTP password is read only through settings/configuration;
- SMTP credentials are never returned through HTML/API responses or logs;
- TLS defaults to enabled;
- production settings fail fast when required SMTP variables are absent or empty;
- the configured SMTP port is validated as an integer in the configuration layer;
- no provider-specific token, SDK, or vendor lock-in is introduced by this authorization.

This record authorizes a settings contract, not SMTP vendor provisioning.

## Development and test behavior

CHG-0004 does not change the frozen intended behavior of non-production modes:

### Development

Development continues to use:

```text
django.core.mail.backends.console.EmailBackend
```

No real SMTP credentials are required for ordinary local development.

### Test

Tests continue to use:

```text
django.core.mail.backends.locmem.EmailBackend
```

Tests must remain deterministic and must never connect to external mail infrastructure.

## Compatibility with BL-ARCH-002

The change is compatible with BL-ARCH-002 because:

- Django remains the account/email application framework;
- email side effects stay behind Django's email abstraction;
- environment access remains settings/configuration-only;
- no new runtime service, frontend framework, database, or architecture style is introduced;
- Issue → branch → PR → CI → peer-review governance remains unchanged.

## Compatibility with BL-DATA-002

This Change Record makes no data-model change.

It does not modify User, OTPChallenge, ReportSubscription, migrations, database constraints, or
lifecycle invariants.

## Compatibility with CHG-0003

CHG-0003 remains authoritative for cache, Celery worker/Beat, and optional Channels Redis runtime
extensions.

CHG-0004 is intentionally separate because CHG-0003 stated that future delivery credentials require
their own settings/configuration contract and explicitly did not authorize new production secrets.

## Baseline handling

BL-FOUNDATION-001 remains immutable historical evidence and is not edited in place.

A separate BL-FOUNDATION-002 is not frozen in Issue #47 because this Change Record authorizes a
target change but does not apply or verify the production SMTP implementation.

The superseding foundation baseline already required before Gate 3 closure must capture the actual
applied state, including:

- final production email environment variables;
- final settings mapping;
- typed environment helper behavior if added;
- development/test email backends;
- applied CHG-0003 runtime changes;
- verification evidence and the exact freeze commit.

## Rollback plan

The authorized production email configuration is operationally reversible:

- remove the production SMTP mapping;
- remove the new email environment-variable contract;
- restore production to its prior unconfigured mail-transport state;
- leave all User, OTPChallenge, ReportSubscription, and other database data untouched.

A rollback does not edit BL-FOUNDATION-001 to hide the historical change.

If a production OTP feature depends on email at the time of rollback, that feature must be treated as
operationally unavailable until another approved delivery configuration exists.

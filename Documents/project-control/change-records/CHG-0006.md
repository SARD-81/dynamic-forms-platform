# CHG-0006 — Gate 4 Production Runtime Topology Authorization

**Status:** APPROVED BY TEAM LEAD / EFFECTIVE ON MERGE  
**Date:** 2026-10-02  
**Issue:** #78  
**Affected foundation:** production runtime/deployment contract derived from BL-FOUNDATION-002  
**Planned superseding baseline after verified implementation:** BL-FOUNDATION-003

## Purpose

Authorize the bounded structural/runtime changes required to satisfy the remaining mandatory production-delivery requirement without rewriting frozen Gate 3 baselines in place.

This Change Record defines the allowed Gate 4 production topology and security/verification boundaries. It does not itself implement that topology.

## Current verified starting point

Gate 4 currently has:

- Python 3.12;
- Django 5.2 LTS;
- Django Channels + Daphne already present through `channels[daphne]`;
- PostgreSQL 16;
- Redis 7;
- Celery worker + Celery Beat;
- development Docker Compose topology using Django `runserver`;
- production settings with `DEBUG=False`, secure cookies, configurable SSL redirect and SMTP configuration;
- no production `STATIC_ROOT`/collectstatic topology;
- no production Nginx service;
- no production-specific Compose path;
- #79 `production_preflight` merged through PR #88 and reusable;
- #82 external production HTTP/static verifier merged through PR #94 and reusable;
- #80 health/readiness/logging implementation available in PR #87 but blocked from merge until this Change Record becomes effective;
- Gate 4 governance transition #89 / CHG-0007 merged through PR #90 and is now effective prospectively for Gate 4.

The development Docker contract remains valid and must continue to work after Gate 4 production work is added.

## Project-brief boundary

The original project brief requires production mode, production-oriented web serving, production settings/static collection, Dockerization and environment-owned configuration.

Reverse proxy usage such as Nginx is bonus/extra-credit scope in the brief. Gate 4 deliberately selects Nginx as the production reverse-proxy/static-serving boundary because it provides one explicit public ingress, efficient collected-static serving and a compatible future boundary for optional WebSocket proxying.

This Change Record therefore authorizes Nginx as the project-selected production topology; it does not claim that Nginx itself is mandated by the brief.

## Decision

This Change Record is approved by the Team Lead as the Gate 4 production-runtime authorization boundary. It becomes effective only when the Team Lead merges this PR to `dev` under CHG-0007. Until that merge occurs, #80/#81 runtime implementation remains merge-blocked.

After CHG-0006 becomes effective, #81 and the runtime portion of #80 may implement the production-oriented runtime described below. No broader infrastructure change is authorized.

## Authorized production topology

A dedicated production-oriented Compose path must be added separately from the existing development `compose.yaml`.

Preferred artifact:

`compose.production.yaml`

The production topology must contain these logical roles:

1. **app-init** — one-shot application initialization using the production Django settings;
2. **web** — Django ASGI application served by Daphne, never Django `runserver`;
3. **nginx** — selected public HTTP reverse-proxy/static-serving boundary;
4. **celery-worker** — scheduled-report worker using production settings;
5. **celery-beat** — scheduled-report scheduler using production settings;
6. **postgres** — PostgreSQL source of truth, internal only;
7. **redis** — cache/Celery runtime dependency, internal only.

A materially equivalent layout is acceptable only if it preserves every security, startup, static-file and verification property below.

## Application image/runtime authorization

The existing application image strategy may be extended for production, but must preserve development behavior.

Authorized requirements:

- production application serving reuses the already-installed Daphne capability; no new production web-server dependency is required;
- the production image must not default to Django `runserver`;
- production containers run with `DJANGO_SETTINGS_MODULE=config.settings.production`;
- no source-code bind mount is allowed in the production-oriented topology;
- runtime/dev dependency separation may be improved if #81 can do so without destabilizing development, but adding a new third-party dependency requires explicit justification;
- the application image must remain reproducible from repository files alone plus environment-owned configuration.

## Initialization contract

The production topology must perform initialization deterministically before the application is considered ready.

Authorized/required initialization actions:

```text
python src/manage.py migrate --noinput
python src/manage.py collectstatic --noinput
python src/manage.py production_preflight
```

The exact orchestration may use a one-shot `app-init` service or an equivalent explicit startup step.

Requirements:

- migration failure prevents successful application startup/acceptance;
- collectstatic failure prevents successful application startup/acceptance;
- production preflight failure prevents successful application startup/acceptance;
- startup must not hide failures behind unbounded retry loops;
- initialization must not manufacture domain data.

## ASGI serving contract

The production web service must serve the existing Django ASGI application directly through Daphne.

Expected command shape:

```text
daphne -b 0.0.0.0 -p 8000 config.asgi:application
```

An equivalent explicit Daphne command is allowed.

The web container must not expose a host port directly in the production-oriented topology. Nginx is the selected public HTTP boundary.

## Static-file contract

Gate 4 must add an explicit production `STATIC_ROOT` and use Django `collectstatic --noinput`.

Requirements:

- collected assets live in a dedicated production static location/volume;
- `app-init` has write access during collection;
- Nginx consumes collected static content read-only where practical;
- `/static/` is served by Nginx rather than proxied to Django;
- at least one representative project/admin static asset is verified through the public Nginx boundary;
- source files, `.env` files, database files, templates and other private repository content must not be exposed as static content;
- development static handling remains unchanged.

The exact internal filesystem path is implementation detail for #81, but it must be explicit and shared consistently between Django collectstatic and Nginx.

## Nginx public-boundary contract

Nginx is authorized as the single public HTTP entrypoint of the production-oriented Compose topology.

Required behavior:

- proxy application traffic to the internal Daphne service;
- serve the configured `/static/` prefix from collected assets;
- preserve the original Host header;
- set a controlled `X-Forwarded-Proto` value based on the trusted proxy boundary;
- pass only required forwarded headers;
- use finite proxy/connect/read/send timeouts;
- do not expose PostgreSQL, Redis, Celery worker or Celery Beat;
- do not expose the internal Daphne port to the host/public network;
- allow the stable liveness/readiness routes from #80 once merged;
- remain compatible with future optional WebSocket `Upgrade` handling for #41 without implementing #41 in this change.

Only the Nginx HTTP entrypoint may be published by the default production-oriented Compose path.

A configurable local/CI host port is allowed for reproducible smoke verification.

## HTTPS / proxy trust contract

Production Django settings may add the minimum proxy-awareness required for a trusted Nginx boundary.

Authorized settings include:

```python
SECURE_PROXY_SSL_HEADER = ("HTTP_X_FORWARDED_PROTO", "https")
```

provided that:

- the Django application is not independently exposed to untrusted clients in the production topology;
- Nginx overwrites the trusted forwarded-proto header instead of passing arbitrary client input through unchanged;
- Host handling remains explicit;
- secure cookies remain enabled in production;
- `SECURE_SSL_REDIRECT` remains production-secure by default.

For local/CI production smoke over plain HTTP, `DJANGO_SECURE_SSL_REDIRECT=false` may be supplied explicitly as a smoke-only environment value to avoid redirect loops. This does not change the secure production default.

No automatic certificate issuance or provider-specific TLS service is authorized by CHG-0006.

## Production environment contract

Production secrets/configuration remain environment-owned and may only be read through the settings/configuration layer.

Existing required production values remain authoritative, including database, Redis/Celery, Django secret/host/origin and SMTP settings.

Gate 4 may add only environment values required by the approved production runtime, such as a configurable public/local smoke port or narrowly-scoped proxy/runtime controls.

Rules:

- no real secrets committed;
- `.env.production.example` or equivalent contains placeholders only;
- business/domain code must not read environment variables directly;
- production configuration must fail clearly when mandatory values are absent;
- CI uses disposable fake values and must not contact real SMTP/API targets.

### Bounded dependency timeout ownership

CHG-0006 explicitly authorizes finite production connection/socket timeout settings for the PostgreSQL and Redis dependencies used by application readiness checks and normal production connectivity.

Authorized settings-level controls include:

- a bounded PostgreSQL connection-establishment timeout configured through Django database settings/options (for example a driver `connect_timeout` value);
- bounded Redis/cache socket-connect and socket/read timeouts configured through the selected Django Redis/cache backend options where supported;
- environment-owned timeout values or narrowly-scoped defaults resolved only in the settings/configuration layer.

Ownership is split without a circular dependency:

- **#80** owns readiness semantics, acceptable dependency-check bounds, failure behavior and tests proving that readiness fails promptly and without secret leakage;
- **#81** owns production-topology/settings wiring for those approved bounds where production-specific environment/default configuration is required;
- either issue may modify `config.settings.production` or shared settings only within this authorized timeout boundary and with synchronized tests/documentation;
- application/domain/Service/Selector/API/task/model code must not read timeout environment variables directly.

The exact numeric values are implementation details for #80/#81, but they must be finite, documented and suitable for deterministic health checks and CI smoke execution. Unbounded dependency connection waits are not authorized.

## PostgreSQL / Redis / Celery contract

The Gate 3 runtime roles remain mandatory:

- PostgreSQL is the authoritative database;
- Redis logical DB 0 remains the Django cache role;
- Redis logical DB 1 remains the Celery broker role;
- Redis logical DB 2 remains reserved for optional Channels integration if #41 is implemented;
- Celery worker and Beat remain active in production-oriented topology;
- scheduled report task registration must remain verifiable;
- PostgreSQL and Redis have no public host ports in the production topology.

No external queue/database provider or HA scheduler design is authorized.

## Health/readiness/logging integration boundary

Issue #80 owns the application-level operational contract.

Stable target routes are expected to be:

- `/health/live/`;
- `/health/ready/`.

#81/Nginx must proxy these like normal application routes and must not reimplement dependency checks in Nginx.

#80 remains responsible for bounded dependency checks and secret-safe logging. CHG-0006 authorizes the settings-level PostgreSQL/Redis timeout controls required to make those checks bounded; #80 owns the readiness semantics/tests and #81 owns production wiring where topology-specific configuration is required. The runtime/settings changes may merge only after CHG-0006 is effective and the PR branch is synchronized with current `dev`.

## Verification-tool integration boundary

### #79 — internal application preflight

#79 is merged through PR #88. #81/#83/#84 must call the existing `production_preflight` command rather than duplicating its settings/database/cache/runtime checks.

### #82 — external HTTP/static verifier

#82 is merged through PR #94. Its verifier remains independent from Compose/Nginx internals and consumes only stable public interfaces:

- configurable base URL;
- login/application reachability;
- API/OpenAPI reachability;
- health routes after #80 stabilizes them;
- representative collected static path after #81 stabilizes it.

#81 and #83 must integrate with this public verifier rather than creating a competing second verification implementation.

### #83 — CI production-smoke

#83 must add deterministic production-topology verification from a clean runner and reuse #79/#82 tooling.

It must not replace the existing development `docker-smoke` job.

## Mandatory production-smoke evidence

Before Gate 4 closure, CI must demonstrate at least:

- production Compose/config validation;
- production application image build;
- clean production topology startup;
- `config.settings.production` is active inside application/Celery boundaries;
- migrations complete;
- collectstatic completes;
- #79 production preflight succeeds;
- Daphne serves the Django ASGI application without `runserver`;
- Nginx is the only intended public HTTP boundary;
- login/API/OpenAPI/health routes traverse Nginx;
- representative collected static asset is served by Nginx;
- PostgreSQL and Redis are healthy/internal;
- Celery worker ping succeeds;
- scheduled report task remains registered;
- #82 external verifier succeeds;
- cleanup runs even on failure;
- logs remain useful without exposing environment secrets.

## Security constraints

- no real production secrets committed;
- no public PostgreSQL/Redis/Celery ports;
- no source-code bind mounts in production;
- no trust of arbitrary client-supplied proxy headers;
- secure cookie defaults preserved;
- DEBUG remains false;
- static serving cannot expose repository/private files;
- error output/logs must not expose passwords, OTPs, resume tokens, SMTP credentials or complete sensitive connection URLs;
- production smoke must never send real email or external report API deliveries.

## Rollback / failure model

The existing development `compose.yaml` remains unchanged as the development fallback contract.

If the Gate 4 production topology fails verification before freeze:

1. do not create/freeze `BL-FOUNDATION-003` or `BL-RELEASE-001`;
2. do not mark Gate 4 closed;
3. revert/fix the implementing PRs on `dev` using normal Issue/PR governance;
4. keep frozen Gate 3 baselines authoritative;
5. tear down disposable production-smoke containers/volumes.

For local/CI disposable production stacks, a documented `docker compose ... down -v` cleanup is acceptable. Destructive production data rollback is outside this repository-only Gate 4 scope.

## Explicitly out of scope

- Kubernetes;
- Terraform/cloud-provider IaC;
- public cloud provisioning;
- automatic certificate issuance;
- multi-host HA/load balancing;
- external managed Redis/PostgreSQL/Celery providers;
- GraphQL/social login;
- domain-model/schema changes;
- WebSocket consumer implementation (#41);
- changing frozen Gate 3 application semantics.

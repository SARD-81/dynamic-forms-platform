# CHG-0008 — Vercel deployment profile

**Status:** authorized implementation slice; effective on verified merge
**Authorization:** project owner requested completion and deployment to Vercel on 2026-10-12,
including provisioning required services.
**Implementation:** [Issue #105](https://github.com/SARD-81/dynamic-forms-platform/issues/105).
The deployment branch is based on the accepted main release; the scoped release
PR targets main after the existing required CI jobs pass.

## Decision

Add a Vercel-specific production profile alongside the accepted Docker profile.
Do not rewrite frozen baselines or replace Django/domain/authentication behavior.

| Role | Vercel profile | Existing Docker profile |
| --- | --- | --- |
| HTTP and templates | ASGI Vercel Function, TLS ingress | Daphne behind Nginx |
| Static assets | collectstatic and Vercel CDN | collected volume and Nginx |
| Database | separate Neon PostgreSQL 16, TLS, pooled runtime connection | PostgreSQL service |
| Shared cache/throttle counters | PostgreSQL cache with advisory locks and atomic increment | Redis |
| Celery tasks | Vercel Queues private subscriber | Redis broker and persistent worker |
| Periodic dispatcher | authenticated daily Vercel Cron | hourly Celery Beat |
| Email | production SMTP through a dedicated Resend sending credential | operator-configured SMTP |

Daily dispatch at 03:00 UTC checks the existing completed weekly/monthly periods.
This satisfies periodic delivery on the Hobby schedule; an hourly schedule needs
a supporting Vercel plan. No report subscription or recipient is created automatically.
Cron returns success only after enqueue succeeds. Existing delivery row locks,
success-only last_sent_at and bounded retries remain authoritative.

PostgreSQL cache avoids a second infrastructure account for this small deployment.
It is shared across function instances and caches expensive aggregate/read models.
Atomic add and increment are essential: Django's default DatabaseCache increment
is not atomic. The adapter serializes writes by key and preserves counter expiry.
Redis remains the default everywhere unless DJANGO_CACHE_BACKEND=postgresql is set.

## Boundaries

Production and CI use separate databases. Migrations are a reviewed one-time
release operation over the direct Neon endpoint, not an action on every HTTP
request or every preview build. Public endpoints retain owner/session/CSRF
permissions. Cron uses a separate random secret and constant-time comparison;
it is disabled outside the Vercel profile. No API key or database credential
belongs in Git, logs or deployment documentation.

Real email acceptance requires a verified sending domain. A deployed page or a
successful SMTP configuration alone does not prove that OTP reaches users.
Optional WebSocket reporting remains outside the accepted mandatory scope.

The release also corrects incomplete OpenAPI schemas for account endpoints,
the process-run steps array and distinct form/process unlock components.
Schema generation must validate with fail_on_warn, with no errors or warnings;
these are documentation accuracy corrections with no authentication behavior change.
The Vercel package declares AnyIO explicitly because the queue adapter's vendored
backend dynamically imports the top-level anyio module during actual task execution.

## Verification and rollback

Run the complete existing suite, lint, migration drift, production checks,
parallel cache add/increment tests, Cron authorization/outage tests and live
HTTP/CSRF/participant/report checks. Preserve existing Docker smoke jobs.
Deploy a reviewed commit and record its exact SHA, URLs and evidence.

Rollback the Vercel release to its previous deployment. Docker settings and
Compose remain usable independently. Neon is durable; never delete production
data as part of deployment rollback.

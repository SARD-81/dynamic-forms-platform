# CHG-0003 — Gate 3 Runtime Extension Authorization

**Status:** APPROVED ON REVIEWED MERGE / NOT YET APPLIED  
**Date:** 2026-09-23  
**Issue:** #39  
**Affected baseline:** BL-FOUNDATION-001  
**Architecture dependency:** BL-ARCH-002  
**Data dependency:** BL-DATA-002

## Purpose

Authorize the smallest controlled extensions to the frozen Gate 2 engineering foundation that are
required by Gate 3 caching, scheduled report delivery, and the optional real-time reporting feature.

This Change Record is an authorization boundary. It does **not** implement runtime changes by itself.

The approval becomes effective only when the Pull Request carrying this record is peer reviewed,
green in CI, and merged to `dev`.

## Why a Change Record is required

BL-FOUNDATION-001 intentionally freezes:

- direct runtime dependency constraints;
- a three-service development Compose topology: `web`, `postgres`, `redis`;
- Celery broker configuration without a worker or Beat service;
- Django Redis cache wiring as deferred;
- Channels Redis backend wiring as deferred;
- WebSocket routing as deferred.

Gate 3 now requires:

- #32 — Django cache activation through Redis logical DB 0;
- #40 — executable Celery worker + Beat runtime for mandatory scheduled report delivery;
- #41 — Redis-backed Channels only if the optional real-time reporting feature is implemented.

Applying those changes without a Change Record would silently violate the frozen foundation contract.

## Decision

CHG-0003 authorizes the controlled runtime extensions below and no broader infrastructure rewrite.

### 1. Mandatory Django cache activation — Issue #32

Issue #32 may configure Django's `CACHES` setting to use the built-in Redis cache backend and the
existing `REDIS_CACHE_URL` configuration value.

Rules:

- logical Redis DB 0 remains reserved for Django cache;
- environment access stays inside settings/configuration;
- domain code uses `django.core.cache`, not a direct Redis client;
- test settings use deterministic local-memory cache unless an integration test explicitly requires Redis;
- PostgreSQL remains authoritative; cache failure must not become a data-integrity failure;
- passwords, OTPs, raw resume tokens, and other credentials must never be cached;
- cache key ownership and invalidation rules must be documented by the implementing Issue.

The current dependency set already installs Redis client support through the frozen
`celery[redis]` requirement. This Change Record does not add a separate direct `redis` constraint.
If the implementing branch cannot satisfy Django RedisCache with the resolved dependency set, it
must amend change control before adding a new direct dependency.

### 2. Mandatory Celery execution runtime — Issue #40

Issue #40 may extend the development Compose topology with exactly these additional services:

- `celery-worker`
- `celery-beat`

The resulting mandatory development topology becomes:

```text
web
postgres
redis
celery-worker
celery-beat
```

Both Celery services must:

- reuse the project application image rather than introducing a separate application image;
- use the same settings/configuration boundary as the web process;
- use logical Redis DB 1 through the existing `CELERY_BROKER_URL`;
- wait for the infrastructure they need instead of replacing existing health checks;
- remain development services only; this Change Record does not define production topology.

Approved command shape for the `src/` layout:

```text
celery --workdir=src -A config worker --loglevel=INFO
celery --workdir=src -A config beat --loglevel=INFO --schedule=/tmp/celerybeat-schedule
```

The Beat scheduler is a separate process. Embedding Beat into the worker with `-B` is not the
approved development topology.

The default Celery Beat scheduler is sufficient for Gate 3. This Change Record does not authorize
`django-celery-beat`, a new scheduler database model, or another scheduling dependency.

Issue #40 owns the actual task definitions, schedules, retries/failure handling, and delivery logic.

### 3. Optional Channels Redis backend — Issue #41 only

If the BONUS Issue #41 is implemented, it may add this direct runtime dependency:

```text
channels-redis>=4.3.0,<4.4
```

It may then configure `CHANNEL_LAYERS` through settings using the existing
`CHANNEL_LAYER_URL`, with logical Redis DB 2 reserved for Channels.

Rules:

- WebSocket serving remains part of the existing Daphne/ASGI web runtime;
- no new WebSocket-specific Compose service is required;
- report subscriptions require authenticated ownership checks;
- events are additive and never the source of truth;
- transaction-dependent events are emitted only after commit;
- no password, OTP, raw resume token, or raw private response payload is broadcast.

If #41 is deferred, `channels-redis` must not be added merely because this Change Record exists.

## Redis logical separation after application

The approved logical separation remains:

```text
DB 0 → Django cache
DB 1 → Celery broker
DB 2 → Channels layer (only when #41 is implemented)
```

A feature must use the framework abstraction assigned to its role:

- Django Cache API for DB 0;
- Celery broker configuration for DB 1;
- Channels layer configuration for DB 2.

No Gate 3 business/domain code may create an ad-hoc Redis client.

## Baseline handling decision

This Change Record selects **controlled extension while BL-FOUNDATION-001 remains immutable
historical evidence**.

A `BL-FOUNDATION-002` is intentionally **not** created in Issue #39 because this Issue does not
apply or verify the runtime changes. Freezing a target topology before it exists would misrepresent
the verified repository state.

A superseding foundation baseline becomes required after the authorized mandatory runtime changes
have actually been implemented and verified, and before Gate 3 closes.

That future baseline must record the implementation that actually landed, including:

- final direct runtime dependency constraints;
- final development Compose services and commands;
- active Django cache configuration;
- active Celery worker/Beat runtime;
- Channels Redis state as implemented or explicitly deferred;
- verification evidence and the exact freeze commit.

BL-FOUNDATION-001 must never be edited in place.

## Compatibility with BL-ARCH-002

The change is compatible with BL-ARCH-002 because it preserves:

- the Django modular-monolith architecture;
- Redis roles for cache, Celery, and Channels;
- Celery + Celery Beat as the scheduled execution mechanism;
- Channels/WebSockets only for real-time reporting;
- settings/configuration as the environment boundary;
- the Issue → branch → PR → CI → peer-review workflow.

No new application architecture style or frontend/runtime framework is introduced.

## Compatibility with BL-DATA-002

This Change Record makes no data-model change.

It does not add, remove, or mutate any persisted domain entity, relation, database constraint, or
lifecycle rule from BL-DATA-002.

Scheduled-report and real-time implementations must continue to read PostgreSQL business records as
the source of truth.

## Security and configuration impact

The authorized extensions must preserve these rules:

- no secrets are committed;
- Redis remains internal to the development Compose network and is not published to the host;
- existing Redis URLs continue to come from settings/configuration;
- business Services, Selectors, views, APIs, tasks, and consumers do not call `os.getenv()`;
- cache/channel data must not contain authentication credentials or raw secret tokens;
- Celery/API delivery credentials, if introduced later, require their own settings/configuration
  contract and must not be embedded in source code.

This Change Record does not authorize new production secrets or a production deployment design.

## Transaction and correctness rules

Runtime extensions must not weaken application correctness:

- database writes remain transactional in Services;
- asynchronous task enqueueing that depends on committed data uses `transaction.on_commit(...)`;
- WebSocket events that depend on committed data use `transaction.on_commit(...)`;
- caching is an optimization and not an authority;
- scheduled delivery failures must not corrupt the underlying report/subscription state.

## Rollback plan

The changes authorized by this record are operationally reversible without changing BL-DATA-002.

### Cache rollback

- remove Redis `CACHES` wiring;
- return test/development behavior to Django's non-Redis cache configuration;
- leave PostgreSQL data untouched.

### Celery runtime rollback

- stop/remove `celery-worker` and `celery-beat` development services;
- disable Gate 3 scheduled dispatch entry points;
- retain the existing broker configuration for later reactivation;
- remove any disposable Beat schedule file.

### Optional Channels rollback

- remove Channels Redis configuration;
- remove `channels-redis` if no remaining feature requires it;
- remove WebSocket routing/consumers while keeping HTTP reporting functional.

Rollback must not edit frozen historical baselines to hide the reverted change.

## Verification plan

### Change-control PR verification

Because Issue #39 is documentation/change-control only, this PR must prove that the frozen runtime
has not been modified while approval is being recorded:

```bash
ruff format --check .
ruff check .
pytest
python src/manage.py makemigrations --check --dry-run
docker compose --env-file .env.example config --quiet
```

CI must keep the stable jobs green:

- `lint`
- `test`
- `migration-check`

The PR must contain no changes to:

- `requirements/base.txt`;
- `compose.yaml`;
- application settings/runtime code;
- models or migrations.

### Downstream application verification

The implementing Issues must add focused verification before their PRs merge.

For #32:

- Redis cache set/get through Django Cache API;
- deterministic test cache behavior;
- cache hit/miss and invalidation tests;
- Redis unavailability must not corrupt authoritative data.

For #40:

- Compose config contains worker and Beat services;
- `web`, `postgres`, and `redis` behavior remains healthy;
- worker connects to Redis DB 1 and executes a test/project task;
- one Beat scheduler process schedules work and the worker consumes it;
- existing pytest settings remain `config.settings.test`;
- fresh Docker bootstrap remains successful;
- direct cross-platform `docker compose` commands are documented.

For #41, if implemented:

- Redis-backed channel layer uses DB 2;
- authorized WebSocket connection succeeds;
- unauthorized/cross-owner connection is rejected;
- HTTP reports remain correct without WebSocket availability.

## Scope boundaries

CHG-0003 does **not** authorize:

- Nginx or production deployment topology;
- Kubernetes or another orchestrator;
- a second Redis service;
- a new database;
- `django-celery-beat`;
- a Celery result backend unless separately justified;
- task/business implementation for scheduled reports;
- WebSocket consumers or reporting logic;
- domain/data-model changes.

Any requirement outside this boundary needs its own reviewed change decision.
